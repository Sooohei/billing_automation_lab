# SR-00 取引先管理 設計

対応システム要件: [SR-00 取引先管理](../requirements/system_requirements/sr-00_partner_management.md)

共通の構成は [全体構成](./architecture.md) を参照。

## 要件との対応

| 要件の振る舞い | 設計での対応 |
|----------------|--------------|
| 1. 取引先を登録・変更・削除できる | [画面](#画面) の登録・変更・削除 |
| 2. 取引先が持つ項目 | [データモデル](#データモデル) |
| 3. freee 申請用の既定値は freee の選択肢から選ぶ | 画面はプルダウンで選ばせ、サーバー側でも `FreeeClient` の一覧にある値か確認する（[入力チェック](#入力チェック) の 6） |
| 4. 登録・変更を受け付けない場合 | [入力チェック](#入力チェック) |
| 5. 送信元メールアドレスは大文字小文字を区別しない | 小文字に正規化して保存・比較する（[正規化](#正規化)） |
| 6. 送信元メールアドレスの変更は次回の SR-01 の取込から反映 | [反映タイミング](#反映タイミング) |
| 7. 既定値の変更は以後に作成される支払い依頼インプットから反映 | [反映タイミング](#反映タイミング) |
| 8. 取引先の変更・削除で作成済みデータを変更しない | 削除は論理削除とし、SR-01〜03 のデータには触れない（[削除](#削除)） |

## データモデル

### `partners`（取引先）

| 列 | 型 | 制約 | 内容 |
|----|----|------|------|
| `id` | UUID | 主キー | 取引先 ID。SR-02・SR-03 から参照する |
| `name` | text | NOT NULL | 取引先名（正規化済み） |
| `freee_partner_id` | bigint | NOT NULL | 既定の freee 上の取引先 |
| `freee_account_item_id` | bigint | NOT NULL | 既定の勘定科目 |
| `freee_tax_code` | bigint | NOT NULL | 既定の税区分 |
| `freee_approval_flow_route_id` | bigint | NOT NULL | 既定の承認経路 |
| `created_at` | timestamptz | NOT NULL | 作成日時 |
| `updated_at` | timestamptz | NOT NULL | 更新日時 |
| `deleted_at` | timestamptz | NULL 可 | 削除日時。NULL なら有効 |

- 部分一意インデックス `uq_partners_name_active`: `UNIQUE (name) WHERE deleted_at IS NULL`
- freee の既定値は freee 上の識別子だけを持つ。表示名は表示のたびに `FreeeClient` から引く

### `partner_emails`（送信元メールアドレス）

| 列 | 型 | 制約 | 内容 |
|----|----|------|------|
| `id` | bigint | 主キー（自動採番） | |
| `partner_id` | UUID | NOT NULL、`partners.id` への外部キー | |
| `email` | text | NOT NULL | 送信元メールアドレス（正規化済み） |
| `created_at` | timestamptz | NOT NULL | 作成日時 |

- 一意インデックス `uq_partner_emails_email`: `UNIQUE (email)`
- 有効な取引先のアドレスだけをこのテーブルに置く。取引先を削除したときはアドレスの行を物理削除する。そのため、一意インデックスに削除済みを除く条件は不要とする（削除した取引先のアドレスは再登録できる）

## 正規化

保存と比較の前に、入力値を次のように正規化する。

| 項目 | 正規化 |
|------|--------|
| 取引先名 | 前後の空白（全角空白を含む）を除く。全角・半角の変換はしない |
| 送信元メールアドレス | 前後の空白を除いて、小文字にする |

送信元メールアドレスの入力欄はテキストエリアにし、1 行に 1 件を入力する。正規化後に空になった行は無視する。

## 入力チェック

登録・変更のたびに、正規化後の値で次の順にすべてチェックする。当てはまったものをまとめて画面に表示し、登録・変更はしない。

| # | 条件 | 要件 | メッセージ例 |
|---|------|------|--------------|
| 1 | 取引先名が空 | 4 | 取引先名を入力してください |
| 2 | 送信元メールアドレスが 1 件もない | 4 | 送信元メールアドレスを 1 件以上入力してください |
| 3 | メールアドレスの形式でないものがある | 4 | 「xxx」はメールアドレスの形式ではありません |
| 4 | 他の有効な取引先と同じ取引先名 | 4 | 取引先名「xxx」は他の取引先に登録されています |
| 5 | 他の有効な取引先に登録済みのアドレスがある | 4 | 「xxx」は取引先「yyy」に登録されています |
| 6 | freee 申請用の既定値のいずれかが空、または freee の選択肢にない | 3、4 | 既定の勘定科目を選択してください |

- メールアドレスの形式: `@` がちょうど 1 つあり、その前後が空でなく、`@` の後ろに `.` を含み、空白を含まないもの。厳密な RFC 準拠のチェックはしない
- 4・5 の「他の取引先」には、変更対象の取引先自身と削除済みの取引先は含めない
- 4・5 は、チェックの後から保存までの間に他の利用者が同じ名前・アドレスを登録した場合でも、DB の一意インデックスで防ぐ。一意制約違反が起きたら、インデックス名から 4・5 のどちらかを判断し、同じメッセージを表示する
- 入力チェックは Pydantic などの自動チェックには乗せず、`service.py` で 1〜6 をまとめて行う。DB や freee の選択肢を参照するチェックを含めて、エラーを 1 回で表示するため

## 処理

### 登録

1 トランザクションで `partners` に 1 行を追加し、`partner_emails` にアドレスの件数分の行を追加する。

### 変更

1 トランザクションで次を行う。

1. 対象の `partners` の行を `SELECT ... FOR UPDATE` でロックする。削除済みまたは存在しない場合は「取引先が見つかりません」と表示する
2. 取引先名・既定値・`updated_at` を更新する
3. 対象の取引先の `partner_emails` を全件削除し、入力されたアドレスを追加し直す

### 削除

1 トランザクションで、`partners.deleted_at` に現在日時を入れ、その取引先の `partner_emails` を全件削除する。

- `partners` の行は残す。SR-02 の抽出結果・SR-03 の支払い依頼インプットが参照する取引先 ID は有効なままで、取引先名も引き続き表示できる
- SR-01 の請求書データ、SR-02 の抽出結果、SR-03 の支払い依頼インプットは変更しない
- 削除済みの取引先は、取引先の一覧・選択肢・SR-01 の取込対象の判定に出さない
- 削除済みの取引先を元に戻す機能は設けない。同じ名前・アドレスで新しく登録し直す

## 反映タイミング

- SR-01 は取込を実行するたびに DB から送信元メールアドレスを読む。SR-00 での変更は、次回の取込から反映される（要件 6）
- SR-03 は支払い依頼インプットを作成するときに、その時点の既定値を支払い依頼インプットにコピーする。既定値を変更しても、作成済みのインプットは変わらない（要件 7）
- 取引先の情報をアプリ内にキャッシュしない

## 他の SR に提供するインターフェース

`PartnerRepository` で提供する。

| メソッド | 内容 | 使う SR |
|----------|------|---------|
| `find_active_by_email(email)` | 送信元メールアドレス（正規化して照合）に対応する有効な取引先を返す。なければ None | SR-01、SR-02 |
| `list_active_emails()` | 有効な取引先の送信元メールアドレスの一覧を返す | SR-01 |
| `list_active()` | 有効な取引先を取引先名の順に返す | SR-03（絞り込み・取引先の選択） |
| `get_including_deleted(partner_id)` | 削除済みも含めて取引先を返す | SR-02、SR-03（作成済みデータの取引先名の表示） |

## 画面

| 画面 | パス | 内容 |
|------|------|------|
| 取引先一覧 | `GET /partners` | 有効な取引先を取引先名の順に表示する。列は取引先名、送信元メールアドレス、既定の freee 上の取引先・勘定科目・税区分・承認経路。各行に変更・削除のボタン |
| 取引先登録 | `GET /partners/new`、`POST /partners/new` | 入力フォーム。登録に成功したら一覧へ戻る。失敗したら入力値を残したままエラーを表示する |
| 取引先変更 | `GET /partners/{id}/edit`、`POST /partners/{id}/edit` | 登録と同じフォームに、現在の値を入れて表示する |
| 取引先削除 | `POST /partners/{id}/delete` | 一覧の削除ボタンから、ブラウザの確認ダイアログを経て送信する。削除後は一覧へ戻る |

入力フォームの項目は次の通り。

| 項目 | 入力方法 |
|------|----------|
| 取引先名 | テキスト |
| 送信元メールアドレス | テキストエリア（1 行に 1 件） |
| 既定の freee 上の取引先 | プルダウン（`FreeeClient.list_partners()`） |
| 既定の勘定科目 | プルダウン（`FreeeClient.list_account_items()`） |
| 既定の税区分 | プルダウン（`FreeeClient.list_taxes()`） |
| 既定の承認経路 | プルダウン（`FreeeClient.list_approval_flow_routes()`） |

保存済みの freee の識別子が `FreeeClient` の一覧にない場合、表示名の代わりに「（freee に存在しない値: {識別子}）」と表示する。変更画面では、プルダウンを未選択の状態にする。

## ローカルでの試し方

1. `docker compose up -d` で PostgreSQL を起動する
2. `.env.example` を `.env` にコピーする
3. `alembic upgrade head` でテーブルを作成する
4. `uvicorn app.main:app --reload` でアプリを起動し、`http://localhost:8000/partners` を開く

freee の選択肢は `sample_data/freee/` のサンプルデータが使われる。

## テスト観点

| 観点 | 内容 |
|------|------|
| 入力チェック | 入力チェック 1〜6 のそれぞれで拒否されること。複数当てはまるときはすべて表示されること |
| 正規化 | 取引先名の前後の空白が除かれること。全角・半角が違う名前は別の名前として登録できること |
| 大文字小文字 | `Billing@A-Media.jp` と `billing@a-media.jp` が重複として拒否されること。`find_active_by_email` で大文字を含むアドレスでも見つかること |
| 変更 | 自分自身の名前・アドレスのままの変更が重複として拒否されないこと。アドレスの追加・削除が反映されること |
| 削除 | 削除後、一覧・`list_active`・`find_active_by_email` に出ないこと。`get_including_deleted` では取れること。同じ名前・アドレスで再登録できること |
| 同時更新 | 一意制約違反が、重複のエラーメッセージとして表示されること |
| freee の選択肢 | 選択肢にない識別子を送ると拒否されること |
