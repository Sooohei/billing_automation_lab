# SR-02 請求書からの必要項目の自動出力 設計

対応システム要件: [SR-02 請求書からの必要項目の自動出力](../requirements/system_requirements/sr-02_invoice_field_extraction.md)

共通の構成は [全体構成](./architecture.md) を参照。

## 要件との対応

| 要件 | 設計での対応 |
|------|--------------|
| 1. SR-01 の取込が終わるたびに、未抽出の請求書データをすべて処理する | 1 時間ごとのバッチで、取込のあとに続けて抽出する（[1 時間ごとのバッチ](#1-時間ごとのバッチ)） |
| 2. 請求書データ 1 件につき抽出結果を 1 件作成する | `extraction_results` の主キーを請求書 ID にする（[データモデル](#データモデル)） |
| 3. 送信元メールアドレスに対応する取引先を選択する | SR-00 の `find_active_by_email` で選ぶ（[取引先の選択](#取引先の選択)） |
| 4. 読み取れた項目は値を保存し、読み取れなかった項目は空にして「読み取れず」と記録する。推測した値は入れない | [読み取り](#読み取り) と [形式チェック](#形式チェック) |
| 5. エラーで抽出結果を作れなかった請求書データは次回再度抽出する | 抽出結果がない請求書データを毎回の処理対象にする（[エラー時の動き](#エラー時の動き)） |
| 6. 作成した抽出結果は上書きしない | 抽出結果がない請求書データだけを処理し、更新する処理を作らない |
| 非機能: 請求書データ作成から 1 時間以内 | 取込と同じバッチで、取込の直後に抽出する |
| 非機能: 抽出結果を削除しない | 削除する処理を作らない |

## データモデル

### `extraction_results`（抽出結果）

| 列 | 型 | 制約 | 内容 |
|----|----|------|------|
| `invoice_id` | UUID | 主キー、`invoices.id` への外部キー | 抽出元の請求書 ID |
| `partner_id` | UUID | NULL 可、`partners.id` への外部キー | 取引先。対応する取引先がなければ NULL |
| `invoice_number` | text | NULL 可 | 請求書番号 |
| `qualified_invoice_issuer_number` | text | NULL 可 | 適格請求書発行事業者登録番号（`T` + 13 桁） |
| `issue_date` | date | NULL 可 | 請求書発行日 |
| `due_date` | date | NULL 可 | 支払期日 |
| `amount_excluding_tax` | bigint | NULL 可 | 税抜金額（円） |
| `tax_amount` | bigint | NULL 可 | 消費税額（円） |
| `amount_including_tax` | bigint | NULL 可 | 税込金額（円） |
| `extracted_at` | timestamptz | NOT NULL | 抽出日時 |

- 主キーが請求書 ID なので、1 件の請求書データに抽出結果は 1 件しかできない（要件 2）
- 抽出項目の「読み取り結果」は、値が NULL なら「読み取れず」、NULL でなければ「読み取り済」とする。値と読み取り結果が食い違わないよう、読み取り結果を別の列には持たない
- 抽出項目の値が NULL になるのは、読み取れなかったときだけ。読み取れた値が 0 円の場合は 0 を入れる

## 1 時間ごとのバッチ

SR-01 の取込と SR-02 の抽出は、1 つのバッチ（`app/jobs/hourly.py`）で続けて行う。

1. DB の advisory lock（`pg_try_advisory_lock`）を取る。取れなければ、前回のバッチがまだ動いているので何もせずに終わる
2. SR-01 の取込を行う（[SR-01 の取込の流れ](./sr-01_gmail_invoice_ingest.md#取込の流れ)）
3. SR-02 の抽出を行う（[抽出の流れ](#抽出の流れ)）。2 で取込全体が止まった場合（Gmail の認証エラーなど）も行う
4. advisory lock を外す
5. 2 か 3 でエラーがあった場合は、ジョブを失敗として終わる

| 環境 | 起動方法 |
|------|----------|
| Google Cloud | Cloud Scheduler が 1 時間ごとに Cloud Run Jobs のジョブを起動する。ジョブは `python -m app.jobs.hourly` を実行する |
| ローカル | `python -m app.jobs.hourly` を手動で実行する |

- 3 は、このバッチで取り込んだものに限らず、抽出結果がない請求書データをすべて処理する。そのため、前回までにエラーになったものも再度抽出される（要件 5）
- 取込と抽出を同じバッチで続けて行うので、請求書データの作成から抽出結果の作成までは、通常 1 回のバッチの中で終わる（非機能要件の 1 時間以内）

## 抽出の流れ

`app/extraction/extract.py` の抽出処理。

1. `extraction_results` がない請求書データを、受信日時の古い順にすべて取る
2. 1 件ずつ次の 3〜6 を行う
3. [取引先の選択](#取引先の選択) をする
4. `FileStorage.load(file_key)` で請求書ファイルを読み出す
5. `InvoiceExtractor.extract(請求書ファイル, ファイル名)` で抽出項目を読み取り、[形式チェック](#形式チェック) をする
6. 1 トランザクションで `extraction_results` に 1 行を追加する

## 取引先の選択

- 請求書データの `sender_email` で、SR-00 の `find_active_by_email` を呼ぶ。見つかった取引先を抽出結果の取引先にする
- 見つからない場合（取込のあとに SR-00 で取引先を削除した、またはアドレスを外した場合）は、取引先を NULL にして抽出結果を作る（ユーザー確認済み）。抽出項目は通常どおり読み取る。SR-03 で、利用者が取引先を選び直せる

## 読み取り

### `InvoiceExtractor`

Gmail と同じく（[全体構成](./architecture.md#gmail-連携)）、`InvoiceExtractor` クラス 1 つで、第 1 段階はサンプル、第 2 段階で Vertex AI の Gemini に中身を置き換える。メソッドの形は 2 つの段階で変えない。実装の切替の仕組みは設けない。

| メソッド | 内容 |
|----------|------|
| `extract(pdf, file_name)` | 請求書ファイルから抽出項目を読み取り、`RawExtraction` を返す。読み取れなかった項目は None |

`RawExtraction` は、抽出項目 7 つを文字列または None で持つ。形式チェック前の値なので、型は揃えない。

| 段階 | `extract` の中身 |
|------|------------------|
| 第 1 段階 | 渡された PDF の SHA-256 を計算し、`sample_data/extraction/{SHA-256}.json` を読んで返す。ファイルがなければ、すべての項目を None で返す。別々の請求書が同じファイル名で届くことがあるため、ファイル名ではなく中身の SHA-256 で探す |
| 第 2 段階 | Vertex AI の Gemini に PDF を渡し、抽出項目を JSON で返させる |

第 1 段階のサンプルの形式:

```json
{
  "invoice_number": "INV-2026-0001",
  "qualified_invoice_issuer_number": "T1234567890123",
  "issue_date": "2026-10-01",
  "due_date": "2026-10-31",
  "amount_excluding_tax": "100000",
  "tax_amount": "10000",
  "amount_including_tax": "110000"
}
```

### Gemini の呼び出し（第 2 段階）

| 項目 | 内容 |
|------|------|
| SDK | Google Gen AI SDK（`google-genai`）を Vertex AI のモードで使う |
| 認証 | アプリケーションのデフォルト認証情報。Google Cloud 上は Cloud Run Jobs のサービスアカウント、ローカルは `gcloud auth application-default login` で得た認証情報を使う。API キーは使わない |
| 設定値 | `GOOGLE_CLOUD_PROJECT`、`VERTEX_AI_LOCATION`、`GEMINI_MODEL`（いずれも要確認） |
| 入力 | PDF のバイト列を、MIME タイプ `application/pdf` のデータとしてそのまま渡す。画像だけの PDF（スキャン）も読める |
| 出力 | 構造化出力（`response_schema`）で、抽出項目 7 つを持つ JSON を返させる。各項目は文字列か null |
| 温度 | 0（同じ PDF に対して結果がぶれにくいようにする） |

プロンプトで指示する読み取りのルール:

- 請求書に書かれている値だけを返す。書かれていない項目、判読できない項目は null にする
- 計算で値を作らない（例: 税込金額と消費税額から税抜金額を計算しない）
- 書かれている条件から値を導かない（例: 「月末締め翌月末払い」から支払期日を計算しない）
- 候補が複数あってどれか決められない場合は null にする
- 日付は `YYYY-MM-DD`、金額はカンマや円記号を除いた整数で返す
- 請求書番号・登録番号は書かれている通りに返す

PDF は Vertex AI に送られる。Vertex AI は、送ったデータをモデルの学習に使わない。

## 形式チェック

`InvoiceExtractor` が返した値を、`app/extraction/validation.py` で項目ごとに次のようにチェックして、保存する値にする。チェックに通らない値は、推測した値が混ざった可能性があるものとみなして NULL（読み取れず）にする。

| 項目 | 前処理 | 通る条件 | 保存する型 |
|------|--------|----------|------------|
| 請求書番号 | 前後の空白を除く | 空でない | text |
| 適格請求書発行事業者登録番号 | 全角を半角にし（NFKC）、ハイフンと空白を除き、先頭の `t` は大文字にする | `T` + 13 桁の数字 | text |
| 請求書発行日・支払期日 | 前後の空白を除く | `YYYY-MM-DD` で、実在する日付 | date |
| 税抜金額・消費税額・税込金額 | 全角を半角にし（NFKC）、カンマと空白を除く | 整数（負の数も可） | bigint |

- 前処理は表記をそろえるだけで、値の中身は変えない
- 金額どうしの整合（税抜金額 + 消費税額 = 税込金額）はチェックしない（要件にないため）

## エラー時の動き

| エラー | 動き |
|--------|------|
| 1 件の請求書データの処理中のエラー（ファイルの読み出し失敗、Gemini の呼び出し失敗、Gemini が JSON を返さない、DB エラーなど） | その請求書データのトランザクションを取り消し、エラーをログに出して次の請求書データへ進む。抽出結果を作らないので、次回のバッチで再度抽出する（要件 5） |
| Vertex AI の一時的なエラー（レート制限、5xx） | SDK の再試行に任せる。それでも失敗した場合は、上の 1 件の処理中のエラーと同じに扱う |
| Vertex AI の認証・権限のエラー | 抽出全体を止め、エラーをログに出す。ジョブは失敗として終わる |

- 一部の項目だけ読み取れなかった、または形式チェックに通らなかった場合はエラーではない。その項目を「読み取れず」にして抽出結果を作る
- 壊れた PDF など、何度やっても失敗する請求書データは、バッチのたびに再度抽出してエラーになる。ログで気づけるようにする

## 制約

- 第 2 段階では、生成 AI が請求書に書かれていない値を返す可能性を、プロンプトの指示と形式チェックで減らす。ただし、形式として正しい誤った値（例: 別の日付）は検出できない。SR-03 で利用者が請求書ファイルと見比べて確認・修正する前提とする

## ローカルでの試し方

### 第 1 段階（サンプルの読み取り結果）

1. [SR-01 のローカルでの試し方](./sr-01_gmail_invoice_ingest.md#第-1-段階サンプルのメール) を行い、請求書データを作る
2. `sample_data/extraction/` に、サンプルのメールの PDF の SHA-256（`shasum -a 256 {PDF}` で確かめられる）をファイル名にした JSON を置く（`python -m app.jobs.hourly` の取込で同時に抽出される）
3. `extraction_results` の行ができていることを確認する

サンプルの読み取り結果は、次の場合を確かめられるように用意する。

| サンプル | 確かめること |
|----------|--------------|
| すべての項目がある | すべての項目が「読み取り済」になる |
| 一部の項目が null | その項目だけ「読み取れず」になる |
| 登録番号がハイフン付き・全角 | `T` + 13 桁にそろえて保存される |
| 日付が実在しない（`2026-02-30`）、金額が数字でない | その項目が「読み取れず」になる |
| JSON ファイルがない | すべての項目が「読み取れず」になる |

### 第 2 段階（Gemini）

1. Vertex AI を使う Google Cloud プロジェクトなどを確認し（Google Cloud の設定のため、作業前に確認する）、`GOOGLE_CLOUD_PROJECT`、`VERTEX_AI_LOCATION`、`GEMINI_MODEL` を `.env` に設定する
2. `gcloud auth application-default login` を実行する
3. `python -m app.jobs.hourly` を実行する

## テスト観点

| 観点 | 内容 |
|------|------|
| 処理対象 | 抽出結果がない請求書データだけが処理されること。抽出結果がある請求書データは上書きされないこと |
| 取引先の選択 | 送信元に対応する取引先が選ばれること。対応する取引先がない場合は取引先が空で抽出結果が作られること |
| 読み取り結果 | 読み取れた項目は値が入り、読み取れなかった項目は空で「読み取れず」になること。0 円は「読み取り済」になること |
| 形式チェック | 形式チェックの各条件で、通る値・通らない値が正しく扱われること |
| エラー | 処理中のエラーで抽出結果が作られず、次回再度抽出されること。他の請求書データの処理は続くこと |
| バッチ | 取込のあとに抽出が行われること。取込全体が止まっても抽出が行われること。advisory lock が取れないときに何もせず終わること |

自動テストでは、`InvoiceExtractor` を、テストごとに読み取り結果を返すテスト用の偽物に差し替える。
