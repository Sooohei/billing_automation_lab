# SR-03 支払い依頼の確認・freee への申請 設計

対応システム要件: [SR-03 支払い依頼の確認・freee への申請](../requirements/system_requirements/sr-03_freee_payment_request.md)

共通の構成は [全体構成](./architecture.md) を、freee の仕様は [freee 連携の実現可能性調査](./freee_feasibility.md) を参照。

## 要件との対応

| 要件の振る舞い | 設計での対応 |
|----------------|--------------|
| 1. 確認・修正画面を開いたときに、条件を満たす事前申請を freee から取得する | `FreeeClient.list_approval_requests`（[freee とのやり取り](#freee-とのやり取り)） |
| 2. 申請番号・件名・金額・申請日とともに一覧表示する | [確認・修正画面](#確認修正画面) の事前申請の欄 |
| 3. 件名で事前申請を検索できる | 取得済みの一覧を、画面上で JavaScript で絞り込む（[確認・修正画面](#確認修正画面)） |
| 4. 1 件の事前申請を選んで紐付ける。複数の請求書に同じ事前申請を紐付けてよい | 支払い依頼インプットに事前申請の識別子を持つ。一意制約は付けない |
| 5. 未申請なら紐付けを変更でき、申請済なら変更できない | [保存](#保存) の申請状態のチェック |
| 6. 事前申請の取得に失敗したら画面に表示し、選べなくする | [確認・修正画面](#確認修正画面) の取得失敗時の表示 |
| 7. 請求書データをすべて一覧表示する。抽出結果がなくても表示する | [一覧画面](#一覧画面) の検索（請求書データを起点に外部結合する） |
| 8. 一覧の列 | [一覧画面](#一覧画面) |
| 9. 支払期日の古い順、空は末尾 | [一覧画面](#一覧画面) の並び順 |
| 10. 受信日時・取引先・申請状態で絞り込む | [一覧画面](#一覧画面) の絞り込み |
| 11. 最初は 10 件、ボタンで次の 10 件を追加 | htmx で次の 10 件の行を追加する（[一覧画面](#一覧画面)） |
| 12. 支払い依頼が不要な請求書も未申請のまま残す | 請求書データを一覧から外す処理を作らない |
| 13. 請求書ファイルと支払い依頼インプットを並べて表示する | [確認・修正画面](#確認修正画面) の左右 2 列の表示 |
| 14. 初めて開いたときに支払い依頼インプットを作り、初期値を入れる | [支払い依頼インプットの作成](#支払い依頼インプットの作成) |
| 15. freee の申請用の項目は freee の選択肢から選ぶ | プルダウンで選ばせ、保存時にも選択肢にある値か確認する（[保存](#保存)） |
| 16. 「読み取れず」の項目を区別できる表示にする | [確認・修正画面](#確認修正画面) の強調表示 |
| 17. 未申請なら全項目を修正でき、申請済なら修正できない | [保存](#保存) の申請状態のチェック。申請済の画面は読み取り専用にする |
| 18. 修正しても抽出結果は変更しない | 支払い依頼インプットは抽出結果と別のテーブルに持ち、抽出結果を更新する処理を作らない |
| 19. 未申請の請求書について申請操作を受け付ける | [申請](#申請) の申請状態のチェック |
| 20. 必須項目が空、または事前申請がない場合は、すべて表示して申請しない | [申請](#申請) の申請前のチェック |
| 21. freee に送信し、操作した利用者を申請者として支払い依頼を申請する | [申請](#申請) と [freee とのやり取り](#freee-とのやり取り) |
| 22. 成功の応答を受けた場合のみ申請済にし、識別子・申請者・申請日時を記録する | [申請](#申請) |
| 23. 失敗・応答なしの場合は未申請のまま、エラー内容または応答なしを表示する | [申請](#申請) のエラー時の動き |
| 24. 応答なしの場合は、再申請の前に利用者が freee 上で確認する | 応答なしのときに、確認を促すメッセージを表示する（[申請](#申請)） |
| 非機能: 一覧・詳細の表示は 3 秒以内 | [応答時間](#応答時間) |
| 非機能: 追加のソフトウェアなしで利用できる | ブラウザだけで使う。PDF はブラウザの PDF 表示で見る |
| 非機能: freee の認証情報を平文で残さない | 本リポジトリでは freee と通信しないため、認証情報を持たない |
| 非機能: 支払い依頼インプットを削除しない | 削除する処理を作らない |

## データモデル

### `payment_request_inputs`（支払い依頼インプット）

| 列 | 型 | 制約 | 内容 |
|----|----|------|------|
| `invoice_id` | UUID | 主キー、`invoices.id` への外部キー | 請求書 ID |
| `partner_id` | UUID | NULL 可、`partners.id` への外部キー | 取引先 |
| `title` | text | NULL 可 | 申請タイトル |
| `invoice_number` | text | NULL 可 | 請求書番号 |
| `qualified_invoice_issuer_number` | text | NULL 可 | 適格請求書発行事業者登録番号 |
| `issue_date` | date | NULL 可 | 請求書発行日 |
| `due_date` | date | NULL 可 | 支払期日 |
| `amount_excluding_tax` | bigint | NULL 可 | 税抜金額 |
| `tax_amount` | bigint | NULL 可 | 消費税額 |
| `amount_including_tax` | bigint | NULL 可 | 税込金額 |
| `freee_partner_id` | bigint | NULL 可 | freee 上の取引先 |
| `freee_account_item_id` | bigint | NULL 可 | 勘定科目 |
| `freee_tax_code` | bigint | NULL 可 | 税区分 |
| `freee_approval_flow_route_id` | bigint | NULL 可 | 承認経路 |
| `pre_application_id` | bigint | NULL 可 | 紐付けた事前申請の freee 上の識別子 |
| `pre_application_number` | text | NULL 可 | 紐付けた事前申請の申請番号（表示用の控え） |
| `pre_application_title` | text | NULL 可 | 紐付けた事前申請の件名（表示用の控え） |
| `created_from_extraction` | boolean | NOT NULL | 作成時に SR-02 の抽出結果があったか |
| `status` | text | NOT NULL、`unsubmitted` か `submitted` | 申請状態（未申請 / 申請済） |
| `freee_payment_request_id` | bigint | NULL 可 | freee 支払い依頼の識別子 |
| `applicant_email` | text | NULL 可 | 申請者（利用者のメールアドレス） |
| `applied_at` | timestamptz | NULL 可 | 申請日時 |
| `created_at` | timestamptz | NOT NULL | 作成日時 |
| `updated_at` | timestamptz | NOT NULL | 更新日時 |

- 主キーが請求書 ID なので、1 件の請求書に支払い依頼インプットは 1 件しかできない
- CHECK 制約: `status = 'submitted'` のときは、`freee_payment_request_id`・`applicant_email`・`applied_at` がすべて NULL でない
- 要件の Output で「必須」の項目も、編集の途中では空がありうるので NULL 可とする。必須かどうかは申請前のチェックで確かめる（[申請](#申請)）
- 事前申請の申請番号と件名を控えとして持つのは、事前申請の取得に失敗したときや、紐付けた事前申請が取得条件を満たさなくなったとき（例: 15 件に達した）にも、紐付けた事前申請を表示できるようにするため
- 申請者は、ログインしている利用者のメールアドレスとする（[全体構成の認証](./architecture.md#認証)。freee のアカウントを使わない間の暫定措置）

## 一覧画面

`GET /invoices`。`GET /` もここへ転送する。

### 表示する行と値

請求書データ（`invoices`）を起点に、抽出結果（`extraction_results`）と支払い依頼インプット（`payment_request_inputs`）を外部結合する。そのため、抽出結果や支払い依頼インプットがない請求書データも表示される（要件 7）。利用者によって表示内容を変えない。

| 列 | 値 |
|----|-----|
| 受信日時 | 請求書データの受信日時（日本時間で表示） |
| 取引先 | 支払い依頼インプットがあればその取引先、なければ抽出結果の取引先。取引先名は SR-00 の `get_including_deleted` で引く |
| 税込金額 | 支払い依頼インプットがあればその税込金額、なければ抽出結果の税込金額 |
| 支払期日 | 支払い依頼インプットがあればその支払期日、なければ抽出結果の支払期日 |
| 申請状態 | 支払い依頼インプットがあればその申請状態、なければ「未申請」 |

- 「支払い依頼インプットがあれば」は、インプットの行があるかで決める。インプットがあってその項目が空なら、抽出結果ではなく空を表示する（利用者が消した値を抽出結果で埋めないため）
- 各行から確認・修正画面へ移れる

### 並び順

支払期日（上の表の値）の古い順。支払期日が空の請求書は末尾に並べる（`NULLS LAST`）。支払期日が同じ場合は受信日時の古い順、それも同じなら請求書 ID の順とし、ページをまたいでも順序がぶれないようにする。

### 絞り込み

画面上部のフォームで指定する（`GET` のクエリ文字列）。複数の条件はすべてを満たす請求書を表示する。

| 条件 | 入力 | 判定 |
|------|------|------|
| 受信日時 | 開始日・終了日（日付）。どちらか一方だけでもよい | 開始日の日本時間 0 時以降、終了日の翌日の日本時間 0 時より前 |
| 取引先 | SR-00 の有効な取引先（`list_active`）から 1 つ選ぶプルダウン | 上の表の取引先が一致する |
| 申請状態 | 未申請 / 申請済から 1 つ選ぶプルダウン | 上の表の申請状態が一致する |

### 次の 10 件の表示

- 最初の表示では、先頭から 10 件を表示する
- 表示していない請求書がある場合は「次の 10 件を表示」ボタンを表示する。11 件目があるかは、11 件を取得して判定する
- ボタンを押すと、htmx で `GET /invoices/rows?offset={表示済みの件数}&{絞り込み条件}` を呼び、返ってきた次の 10 件の行（とボタン）を一覧の末尾に追加する。ページ全体は読み込み直さない

## 支払い依頼インプットの作成

確認・修正画面（`GET /invoices/{id}`）を開いたときに、その請求書の支払い依頼インプットがなければ作成する（要件 14）。同時に開かれても 1 件しかできないよう、`INSERT ... ON CONFLICT (invoice_id) DO NOTHING` で作成する。

初期値:

| 項目 | 抽出結果がある場合 | 抽出結果がない場合 |
|------|--------------------|--------------------|
| 取引先、請求書番号〜税込金額 | 抽出結果の値 | 空 |
| freee 上の取引先・勘定科目・税区分・承認経路 | その時点の取引先（SR-00）の既定値。取引先が空なら空 | 空 |
| 申請タイトル | `{申請月}_{媒体名}_メディア費` | 空（媒体名が空のため） |
| 事前申請 | 空 | 空 |
| `created_from_extraction` | true | false |
| 申請状態 | 未申請 | 未申請 |

- 申請月は、作成した日の日本時間の年月を `YYYYMM` にした文字列
- 媒体名は、取引先の取引先名（SR-00）。取引先が空なら申請タイトルは空
- 抽出結果がない状態で作成した場合、その後に抽出結果ができても反映しない（作成済みのインプットを更新する処理を作らない）
- 作成後に取引先を変更しても、freee 申請用の項目と申請タイトルは入れ直さない（[システム要件の考慮しない事項](../requirements/system_requirements/README.md#本要件で考慮しない事項)）

## 確認・修正画面

`GET /invoices/{id}`。左右 2 列で表示する（要件 13）。

| 位置 | 内容 |
|------|------|
| 左 | 請求書ファイル。`<iframe>` で `GET /invoices/{id}/file` を表示する。このパスは `FileStorage` から PDF を読み出し、`Content-Type: application/pdf`、`Content-Disposition: inline` で返す。ブラウザの PDF 表示で見られる |
| 右 | 支払い依頼インプットの入力フォームと、事前申請の欄。下に「保存」「申請」のボタン |

入力フォームの項目:

| 項目 | 入力方法 |
|------|----------|
| 取引先 | プルダウン（SR-00 の `list_active`）。現在の取引先が削除済みの場合は、その取引先も「（削除済み）」を付けて選択肢に残す |
| 申請タイトル | テキスト |
| 請求書番号、適格請求書発行事業者登録番号 | テキスト |
| 請求書発行日、支払期日 | 日付の入力欄 |
| 税抜金額、消費税額、税込金額 | 数値の入力欄 |
| freee 上の取引先、勘定科目、税区分、承認経路 | プルダウン（`FreeeClient` の各一覧） |

保存済みの freee の識別子が `FreeeClient` の一覧にない場合（freee 側で選択肢が削除された場合など）は、SR-00 と同じ扱いにする。

- 未申請の画面: プルダウンを未選択にし、その横に「保存済みの値（識別子: {識別子}）は freee の選択肢にありません。選び直してください」と表示する。そのまま保存すると空になる
- 申請済の画面: 表示名の代わりに「（freee に存在しない値: {識別子}）」と表示する

事前申請の欄:

- 画面を開いたときに `FreeeClient.list_approval_requests` を呼び、事前申請の一覧を、申請番号・件名・金額・申請日とともにラジオボタンで表示する（要件 1、2）
- 一覧の上に件名の検索欄を置く。入力すると、件名に入力した文字列を含む事前申請だけを表示するよう、画面上の JavaScript で絞り込む。freee には問い合わせ直さない（要件 3）
- 紐付けている事前申請があれば、控えの申請番号・件名で表示する
- 取得に失敗した場合は「事前申請を取得できませんでした」と表示し、ラジオボタンを出さない。紐付けている事前申請の表示と、他の項目の修正・保存はできる（要件 6）

「読み取れず」の強調表示（要件 16）:

- `created_from_extraction` が true で、抽出結果のその項目が空（読み取れず）のとき、その入力欄に色を付け、「読み取れず」と添える
- 利用者が値を入れた後も、抽出結果で読み取れなかった項目であることは表示し続ける

申請済の場合:

- すべての項目を読み取り専用で表示し、「保存」「申請」のボタンを出さない。freee 支払い依頼の識別子・申請者・申請日時を表示する

## 保存

`POST /invoices/{id}/save`。

1. 対象の支払い依頼インプットを `SELECT ... FOR UPDATE` でロックする
2. 申請済なら「申請済のため修正できません」と表示して終わる（要件 5、17）
3. 入力チェックをすべて行う。当てはまったものをまとめて表示し、保存しない
4. 入力値で支払い依頼インプットを更新する

- 同じ請求書を複数の利用者が同時に修正した場合は、後から保存した利用者の値で上書きする。修正の競合は検出しない（[システム要件の考慮しない事項](../requirements/system_requirements/README.md#本要件で考慮しない事項) の「同じ請求書の同時申請」と同じく、防がない）

入力チェック（空はどの項目でも許す。空かどうかは申請前に確かめる）:

| 項目 | 条件 |
|------|------|
| 取引先 | SR-00 の有効な取引先、または現在の取引先 |
| 適格請求書発行事業者登録番号 | `T` + 13 桁の数字 |
| 請求書発行日、支払期日 | 実在する日付 |
| 税抜金額、消費税額、税込金額 | 整数 |
| freee 上の取引先・勘定科目・税区分・承認経路 | `FreeeClient` の各一覧にある値 |
| 事前申請 | 現在の値から変わっていない、または `list_approval_requests` の一覧にある。一覧にあれば申請番号・件名の控えも更新する。取得に失敗した場合に変更しようとしたら、エラーとする |

保存に成功したら、確認・修正画面を表示し直す。

## 申請

`POST /invoices/{id}/apply`。「申請」ボタンは、画面の入力値を保存したうえで申請する（ユーザー確認済み）。

1. [保存](#保存) と同じ処理をする。入力チェックに当てはまった場合は、保存も申請もせずに表示する
2. 新しいトランザクションで、対象の支払い依頼インプットを `SELECT ... FOR UPDATE` でロックする
3. 申請済なら「申請済です」と表示して終わる（要件 19）
4. 申請前のチェックをする。次のうち当てはまるものをすべて表示し、申請しない（要件 20）。1 で保存した値は残る
   - Output で必須の項目のうち空のもの: 取引先、申請タイトル、請求書発行日、支払期日、税込金額、freee 上の取引先、勘定科目、税区分、承認経路
   - 事前申請が紐付けられていない
5. `FileStorage` から請求書ファイルを読み出し、`FreeeClient.upload_receipt` でアップロードする
6. `FreeeClient.create_payment_request` で支払依頼を申請する（項目の対応は [freee とのやり取り](#freee-とのやり取り)）
7. 成功したら、申請状態を申請済にし、freee 支払い依頼の識別子・申請者（ログインしている利用者のメールアドレス）・申請日時を記録してコミットする（要件 22）

- 5〜6 の間も 2 のロックを持ち続ける。そのため、同じ請求書の申請ボタンを続けて押しても、2 回目は 3 で止まる
- 二重送信を防ぐため、申請ボタンは押したら JavaScript で押せなくする

エラー時の動き（要件 23、24）。いずれもロックを外して申請状態は未申請のままにし、確認・修正画面にメッセージを表示する。

| エラー | メッセージ |
|--------|------------|
| freee がエラーを返した（`FreeeApiError`） | 「freee への申請に失敗しました: {freee が返したエラー内容}」 |
| freee から応答を受け取れなかった（`FreeeNoResponseError`。タイムアウト、接続失敗） | 「freee から応答を受け取れませんでした。freee 上で申請されている可能性があります。再度申請する前に、freee 上でこの請求書の支払依頼が申請されていないことを確認してください」 |

- 5 のアップロードに成功し、6 で失敗した場合、freee のファイルボックスにファイルが残る。再度申請すると、もう一度アップロードする（残ったファイルは使わない）

## freee とのやり取り

`FreeeClient`（[全体構成](./architecture.md#freee-連携)）に次のメソッドを追加する。`user` はログインしている利用者で、freee に実接続するときに利用者ごとの freee の認可を使うための引数（サンプルでは使わない）。

| メソッド | 内容 | エラー |
|----------|------|--------|
| `list_approval_requests(user)` | 紐付けできる事前申請の一覧を返す。要件 1 の取得条件をすべて満たすものだけを返す | 取得に失敗したら例外 |
| `upload_receipt(user, pdf, file_name)` | 請求書ファイルを freee のファイルボックスにアップロードし、識別子を返す | `FreeeApiError`、`FreeeNoResponseError` |
| `create_payment_request(user, params)` | 支払依頼を申請中（`draft: false`）で作成し、識別子を返す | `FreeeApiError`、`FreeeNoResponseError` |

`list_approval_requests` が返す事前申請の項目: `id`（freee 上の識別子）、`application_number`（申請番号）、`title`（件名）、`amount`（金額）、`application_date`（申請日）。

`create_payment_request` の `params` と freee の支払依頼の項目の対応（[freee 連携の実現可能性調査](./freee_feasibility.md#支払い依頼インプットと-freee-項目の対応)）:

| 支払い依頼インプット | freee 支払依頼 |
|----------------------|----------------|
| 申請タイトル | `title` |
| freee 上の取引先 | `partner_id` |
| 請求書番号 | `document_code` |
| 請求書発行日 | `issue_date` |
| 支払期日 | `payment_date` |
| 税込金額、勘定科目、税区分 | `payment_request_lines` の 1 行（`amount`、`account_item_id`、`tax_code`） |
| 承認経路 | `approval_flow_route_id` |
| 紐付けた事前申請 | `parent_id` |
| `upload_receipt` が返した識別子 | `receipt_ids` |

適格請求書発行事業者登録番号、税抜金額、消費税額は freee に送らない（freee の支払依頼に対応する項目がないため）。

### サンプルの動き（`SampleFreeeClient`）

| メソッド | 動き |
|----------|------|
| `list_approval_requests` | `sample_data/freee/approval_requests.json` を読み、要件 1 の取得条件で絞り込んで返す。利用者による違いはない |
| `upload_receipt` | 何も保存せず、新しい識別子を返す |
| `create_payment_request` | 何も保存せず、新しい識別子を返す。常に成功する |

`approval_requests.json` の形式。取得条件の判定に使う項目も持たせる:

```json
[
  {
    "id": 5001,
    "application_number": "A-0001",
    "title": "2026年10月 媒体費 Aメディア",
    "amount": 110000,
    "application_date": "2026-09-20",
    "status": "approved",
    "deal_created": false,
    "manual_journal_created": false,
    "child_request_count": 0
  }
]
```

- サンプルは申請しても `child_request_count` を増やさない
- サンプルは常に成功するので、申請に失敗したとき・応答がなかったときの表示は、自動テストで `FreeeClient` を偽物に差し替えて確かめる

## 応答時間

非機能要件「一覧・詳細の表示はいずれも 3 秒以内（事前申請の取得を含む）」への対応:

- 一覧は、請求書データが毎月 60 件程度（1 年で 720 件程度）なので、1 回の SQL で絞り込み・並び替え・10 件の取得をする。`invoices.received_at` にインデックスを付ける
- 確認・修正画面は、`list_approval_requests` にタイムアウト（2 秒）を設ける。タイムアウトしたら取得の失敗として扱い（要件 6）、画面は 3 秒以内に表示する
- `upload_receipt`・`create_payment_request` のタイムアウトは 30 秒とする（申請は表示ではないため、3 秒の対象外とする）
- Google Cloud 上では、しばらく使われなかった後の最初の表示が 3 秒を超えることがある（[全体構成の制約](./architecture.md#制約)）

## ローカルでの試し方

1. [SR-02 のローカルでの試し方](./sr-02_invoice_field_extraction.md#第-1-段階サンプルの読み取り結果) を行い、請求書データと抽出結果を作る
2. `sample_data/freee/approval_requests.json` に事前申請のサンプルを置く
3. `uvicorn app.main:app --reload` でアプリを起動し、`http://localhost:8000/invoices` を開く

事前申請のサンプルは、次の場合を確かめられるように用意する。

| サンプル | 確かめること |
|----------|--------------|
| 承認済み・件名に「媒体費」・制約を満たす | 一覧に出る |
| 申請中（承認済みでない） | 一覧に出ない |
| 件名に「媒体費」を含まない | 一覧に出ない |
| 取引を作成済み、振替伝票を作成済み | 一覧に出ない |
| 作成した申請が 15 件 | 一覧に出ない |

## テスト観点

| 観点 | 内容 |
|------|------|
| 一覧の行 | 抽出結果・支払い依頼インプットがない請求書データも表示されること |
| 一覧の値 | インプットがあればインプットの値、なければ抽出結果の値が出ること。インプットで消した値が空で出ること |
| 並び順 | 支払期日の古い順で、空が末尾になること。ページをまたいでも重複・抜けがないこと |
| 絞り込み | 受信日時（開始日のみ・終了日のみ・両方）、取引先、申請状態のそれぞれと組み合わせで正しく絞り込まれること |
| 次の 10 件 | 11 件目以降があるときだけボタンが出て、押すと次の 10 件が追加されること |
| インプットの作成 | 抽出結果の有無それぞれで初期値が正しいこと。申請タイトルの申請月・媒体名。2 回目以降に開いても作り直されないこと |
| 事前申請 | 取得条件を満たすものだけが出ること。件名の検索で絞り込まれること。取得に失敗したときにメッセージが出て選べないこと |
| 読み取れず | 抽出結果で読み取れなかった項目が強調表示されること |
| 保存 | 入力チェックの各条件。申請済は保存できないこと。抽出結果が変わらないこと |
| 申請前のチェック | 必須項目の空と事前申請なしが、すべてまとめて表示されること |
| 申請 | 成功で申請済になり、識別子・申請者・申請日時が記録されること。freee に送る項目が対応表どおりであること |
| 申請のエラー | freee のエラー・応答なしで未申請のままになり、それぞれのメッセージが出ること |
| 二重申請 | 申請済の請求書の申請が拒否されること |
